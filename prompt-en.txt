# AI Project Design and Collaboration System Initialization Prompt

Establish or maintain actionable architecture, development, and testing constraints for the current project.
The project may be implemented primarily by AI, so future AI agents must be able to determine clearly:
where business rules belong, where to change code, how to verify changes, and what remains unfinished.

The goal is not to generate as many documents as possible, but to let the software evolve sustainably,
avoiding mixed responsibilities, duplicated rules, implicit dependencies, and unverifiable local patches.

## 1. Execution Boundaries

By default, start with read-only analysis, present a concrete proposal for user review, and then initialize the documentation.

If the user has already explicitly approved a concrete proposal, do not request approval again.
If the user requests analysis only, do not modify files.
Initializing collaboration documentation does not automatically authorize product code refactoring, database migrations, or on-site configuration changes.

For existing projects, identify and reuse the existing system first; do not blindly overwrite it.
For new projects without source code, design from requirements and explicitly labeled assumptions; do not fabricate implementation evidence.

## 2. Understand the Business Before Designing the Architecture

Before starting, read existing AGENTS.md, MEMORY.md, AI_BOARD.md,
README, build configuration, core source code, tests, and CI.
If a feature map exists, read its index and the entries relevant to the current scope.

Ignore dependency directories, caches, and generated artifacts; read lockfiles when needed to confirm dependency versions.

First establish:

1. Who the software serves and what problem it solves.
2. Core business workflows and acceptance criteria.
3. What belongs to this system and what external systems are responsible for.
4. Who produces and owns the data, and who is allowed to modify it.
5. What is live state, what is a persisted record, and what is a historical snapshot.
6. Whether concurrency, offline operation, retries, asynchronous synchronization, or device control is involved.
7. Deployment model, operating scale, performance, and reliability requirements.
8. What is explicitly out of scope for now.

Ask the user only about unknown conditions that would materially change the architecture.
Record other conditions as verifiable assumptions; do not invent business rules.

Distinguish the following evidence categories:

- Current implementation: supported by source code, runtime configuration, and test evidence.
- Target requirements: supported by user requirements and approved decisions.
- Proposed adjustments: explicitly labeled as proposals, not presented as already implemented.
- To be confirmed: missing facts and their consequences.

When source code deviates from an approved design, record the deviation.
Do not treat an implementation as a correct standard simply because the code already works that way.

## 3. Choose an Architecture Appropriate to the Scale

Prefer a modular monolith unless independent deployment, isolation, scaling,
or similar requirements actually call for multiple services.

Divide modules by business capability, then define responsibilities within each module.
Do not mechanically create every layer, interface, factory, and mapping object for every simple feature.

Where applicable, define these responsibilities:

### Presentation Layer

Owns input, interaction, user review, and display.
Frontend validation supports user experience; the backend must also enforce critical rules.
Call APIs through a shared client instead of scattering authentication and transport details.

### API / Transport Adapter Layer

Owns authentication and authorization, request parsing, basic format validation, invoking business use cases,
and mapping results and errors to interface responses.
It must not gradually take on complex business workflows.

The same business operation exposed through HTTP, MCP, CLI, or message entry points
should reuse the same use case or business service rather than implement rules separately.

### Application Service Layer

Owns use case orchestration, operation ordering, transaction coordination, idempotency,
and invoking domain rules, persistence, and external systems.

Define states such as success, failure, processing, and unknown outcome.
Do not equate “request accepted” with “business operation completed.”

### Domain Layer

Owns business concepts, state transitions, and invariants that must always hold.
Core rules should be testable with as little dependence as possible on HTTP, UI, databases, or vendor protocols.

Simple CRUD does not require a complex domain model.

### Data Access Layer

Owns queries, persistence mapping, transactions, database locks,
uniqueness constraints, and conditional updates for concurrency control.
It must not orchestrate workflows unrelated to data access.

### Infrastructure Layer

Owns database connections, messaging protocols, file systems,
external services, device communication, and runtime environment adapters.

Vendor-specific protocols must not spread into general business rules.

Clearly diagram or list the allowed dependency directions:
domain rules do not depend on UI, transport frameworks, or concrete infrastructure;
application services use persistence and external capabilities through explicit boundaries;
the composition root wires concrete implementations together.

Introduce interfaces only when needed to isolate external dependencies, replace implementations, or test critical behavior.
Do not create a matching interface for every class or function.

### Make Layering an Executable Contract

Layering defines responsibilities and dependencies; creating directories alone does not establish it.
Build a layering contract from business modules and the actual implementation, recording at least:
layer or boundary names, owned and forbidden responsibilities, actual code paths (labeled as planned when not implemented),
public entry points and inputs/outputs, allowed and forbidden dependency directions, authoritative ownership of rules and data,
and verification commands or inspection methods.

Distinguish source-code dependencies from runtime calls and data flows; call order is not a dependency rule.
Keep one authoritative implementation of each business rule. Modules collaborate through public contracts,
without accessing another module's internals or bypassing its data ownership.
Explain why any layer is merged or omitted and which boundaries still apply; do not add empty layers for appearance.

Store the effective contract in an existing architecture document or a single authoritative document under .ai/docs/.
Put actionable prohibitions and checks in .ai/instructions/ with a reference to that contract.
Link each critical constraint to an existing type, lint, dependency, test, or CI check where practical;
add a minimal missing check only within the authorized scope, and label manual checks honestly.
AGENTS.md, relevant task templates, and tool entry points must specify its path and reading triggers.
Record implementation deviations and pending issues in work items; do not promote temporary bypasses into permanent rules.

## 4. Establish Key Design Constraints

Address each relevant scenario; mark non-applicable items as such instead of expanding them mechanically.

1. State ownership:
   Identify the authoritative source of current state and how caches and replicas are updated.

2. Saving and taking effect:
   Determine whether saving a definition, applying runtime configuration, and executing an external action are separate operations;
   define success for each.

3. Consistency:
   Identify changes that must share a transaction;
   do not assume atomicity across databases or external devices.

4. Concurrency:
   Explain how to prevent duplicate operations, stale pages overwriting newer configuration, and state races.

5. Retries:
   Identify operations that can be retried safely;
   explain how to query and reconcile an unknown outcome after a timeout.

6. Asynchronous processing:
   Specify whether queues are durable and how overload is handled;
   identify the point at which data becomes durably persisted.

7. History:
   Identify configuration and data that must be frozen;
   later changes must not silently alter historical meaning.

8. Protocols:
   Explain how external messages map to a unified internal representation;
   define the interpretation of values, units, quality, and time.

9. Security:
   Define authentication, authorization, sensitive information protection, and necessary auditing.

10. Compatibility:
    Explain transitions between old and new interfaces, data structures, and versions;
    specify where compatibility code belongs and when it may be removed.

Each key constraint should identify its implementation location or planned location,
and a test or inspection method.

## 5. Walk Through Core Workflows Before Coding

Choose at least two of the most critical business workflows:
one user-initiated operation and one asynchronous or background workflow.
If the project has no background workflow, choose another critical use case.

List each step, including:

- Entry point and identity;
- Parameter and business validation;
- Modules involved;
- Data reads and writes;
- Transaction and concurrency boundaries;
- External calls;
- Failure and recovery behavior;
- How the outcome is confirmed;
- Corresponding tests.

If an operation requires duplicated business rules across entry points,
or one module carries too many unrelated responsibilities, adjust the design first.

## 6. Establish Lean Documentation with a Single Source of Truth

Reuse or create:

AGENTS.md
MEMORY.md
AI_BOARD.md
.ai/instructions/
.ai/docs/

Add only when genuinely needed:

.ai/skills/
.ai/agents/
.ai/prompts/
Editor adapter files

### AGENTS.md

Keep it short as the project entry point and constraint summary.
Include project boundaries, technology stack, module navigation, key architecture rules,
required reading, verification commands, and operational boundaries.

Do not copy complete design documents here.
Reference the feature map's actual path: read its index when locating a capability,
and read the relevant entries before changing or verifying user-facing behavior.
Also name the actual project verification-contract path established or reused under section 8,
and require reading the relevant procedure before running verification.

### MEMORY.md

Record only the current phase, summaries of effective decisions, recent outcomes, and necessary context.
Archive lengthy completed history rather than appending logs indefinitely.
AI_BOARD.md is authoritative for active issues; avoid maintaining multiple copies of their state.

### AI_BOARD.md

The sole active work board.
Record open / in_progress / blocked items, their impact, next steps, and evidence.
Archive full evidence for closed items and retain necessary links.

### Parallel Work When Needed

A work item's delivery and acceptance boundary does not limit it to one executor.
When parallel work helps, keep the existing board as the task-level authority; record subtask details
in the existing plan or work-item records, splitting files only when useful. This is not a second board.
Assign one overall owner, with integration responsibility unless explicitly delegated in the plan.
Record each subtask's ID, owner, dependencies, write scope, isolated workspace/runtime resources,
status and next step, completion evidence, and handoff. A subtask's progress is not the overall task status.
If subtasks share one record file, its designated writer updates it serially while workers submit separate events;
use separate files when workers need to update their own records directly.

Designate writers for shared requirements, contracts, board and memory summaries, and feature-map indexes or entries.
Workers update only their assigned records and outputs and submit shared-document changes to the designated writer.
In one shared workspace, a file has one writer at a time; handoff records the current revision, next action,
and released resources before the successor takes over. Isolated branches may change the same logical file,
but a named integrator resolves conflicts and verifies the integrated result. Separate branches or worktrees
do not isolate running instances: also isolate ports, data, accounts, profiles, and output paths as needed;
serialize use of resources that cannot be isolated. Coordinate shared-contract changes before dependent work proceeds.
For single-executor work, omit subtask records and additional coordination roles.

### Stable Design Documents

Reuse existing documents first. Split them according to project complexity, covering at least:

- System boundaries and module responsibilities;
- Dependencies between layers and key call flows;
- Data ownership, state, and consistency rules;
- Interface and error contracts;
- Test strategy and release conditions.

These may live in a single architecture document; do not require a separate file for every topic.
For major or hard-to-reverse decisions, write a short ADR:
context, choice, rationale, costs, and conditions for reconsideration.

Clearly distinguish the current state, target state, and migration plan.

### Feature Map: User Journeys and Verification Navigation

Maintain a lightweight map of how users reach and use capabilities and how an agent can verify them.
Start with 3–5 core features identifiable from routes, commands, menus, or documentation;
use fewer if the project has fewer, and expand as work requires rather than documenting everything upfront.
Reuse a section in existing documentation for small projects. When separate files become useful,
use an index such as .ai/docs/feature-map/README.md with details split by feature as needed.
Keep one maintained location for each journey; link an existing verification map instead of duplicating it.

Each entry records:

- User goal and capability, including relevant sub-features and alternative entry points.
- Entry path and prerequisites: identity, permissions, configuration, data, and how to reach a usable starting state.
- Actual steps and driving method: reuse existing verification scripts or harnesses first;
  link the actual project document and subsection established or reused under section 8 for shared launch, readiness, instance isolation, and cleanup instructions, and give concrete commands or stable selectors where available.
- Observable success: the action and resulting state, including relevant persisted or external effects;
  an accepted request or a final screenshot alone may not prove completion.
- Links to related implementation, authoritative business and layering contracts, and tests or acceptance procedures;
  label missing implementation as planned rather than inventing paths or commands.
- Evidence basis: distinguish source-inferred / pending live verification from behavior actually exercised,
  linking to the version, environment, result, and evidence in verification records when available.

The map is navigation and a maintained verification recipe, not a test result or a second business-rule source.
Keep task status and test logs in their existing authoritative locations; reference them instead of copying them.
For new projects, record intended journeys as planned; do not imply they already run.
When journeys change, check the index and affected entries and links. Distinguish documentation drift,
harness gaps, and product bugs; never weaken an expected journey or rewrite documentation to conceal a bug.

### Coding Standards

Keep them short, concrete, and checkable.
Specify where code belongs, which dependencies are forbidden, and how to verify compliance.
Avoid vague requirements such as “maintain high cohesion” that cannot be executed directly.

The existence of a documentation directory does not mean tools will load it automatically.
AGENTS.md and tool entry points must specify when to read each resource.
Editor adapters reference the authoritative source instead of copying the full rules;
generate only formats confirmed to be supported by the current tools.

## 7. Workflow for Every Subsequent Implementation

Before changing anything:

1. Read relevant constraints and current work items. Locate the affected feature-map entries, user entry points, and verification recipes; add or extend an entry when the capability is missing, without expanding into an unrelated inventory.
2. Reference the layering contract and state the business module, layer, target paths, and cross-layer calls involved. Establish ownership before choosing an implementation location; do not place logic in an entry point merely for convenience.
3. Search for existing rules and implementations, and prioritize reuse.
4. Assess effects on interfaces, persistence, state, permissions, and recovery.
5. Define the acceptance method.

Before scaling parallel work that depends on the same verification setup, prove one minimal
launch–drive–assert–capture–cleanup loop using section 8. If unavailable, identify the blocked checks;
independent analysis or work that does not depend on that environment can continue.

During implementation:

- Fix the responsibility or logic causing the error instead of unconditionally adding fallback branches.
- Do not duplicate existing business rules in another layer.
- Do not use defaults to hide missing data, failures, or unknown states.
- Do not manufacture success by weakening tests or swallowing errors.
- Do not perform broad refactoring of unrelated modules as a side task.
- Do not introduce unauthorized compatibility mechanisms or new infrastructure.

If an architecture boundary really needs to change:
explain why and what it affects, and update decisions and tests together.
Submit a concrete proposal first when the change involves data destruction,
major changes to business semantics, or an expansion of authorization scope.

After implementation:

- Run verification appropriate to the risk;
- Exercise the affected user journeys using their mapped entry points and driving methods, checking observable outcomes and relevant side effects. Record actual coverage and evidence in verification records; explain failures, unexecuted steps, and blockers without counting them as passes;
- Check callers and other entry points, plus new dependencies, layer bypasses, circular dependencies, duplicated rules, and data ownership;
- Update changed contracts and necessary documentation;
- Update affected feature-map entries and index links to reflect confirmed journey or harness changes, preserving the distinction between source inference and live evidence;
- For parallel work, the integrator verifies the affected contracts and user journeys on the integrated revision; separate branch passes do not establish integrated success. Route shared updates through their designated writers;
- Report passes, failures, checks not run, and remaining risks.

Choose roles according to the actual task; a role does not require launching multiple agents
or automatically grant permission for external operations.

## 8. Use Tests to Verify the Design

Establish tests according to risk:

- Pure business rule tests;
- Business use case and state transition tests;
- Database transaction and concurrency integration tests;
- External protocol contract tests;
- Critical user workflow tests;
- Failure recovery and permission tests.

When asynchronous processing or device control is involved, cover:
duplicate requests, timeouts, out-of-order events, disconnections, partial success,
process interruption, and data consistency after recovery.

For critical boundaries maintained by AI,
use lint, dependency checks, type checks, or automated tests wherever possible;
do not rely solely on AI reading documentation and voluntarily following it.

### Verification Capability Contract

Reuse the existing test strategy, acceptance procedure, or verification skill for the shared recipe;
one short section can suffice. Do not require a new CLI, skill, service, or directory.
Prefer existing tools for deterministic steps. Add a small helper only when useful and authorized,
documenting its invocation, inputs/outputs, failure behavior, and cleanup.

Cover the applicable parts of this loop:

1. Launch: the documented command or operation, configuration, auth, data, and prerequisites for a usable state.
2. Identify and check: confirm the intended instance, build/revision, and isolated resources; check readiness,
   not only a running process or open port. Recheck after surprising behavior; reset or relaunch when needed.
3. Drive: use the actual user entry and input path with concrete steps or stable handles.
   Internal handlers or state assignments cannot substitute for that path. Mocks may isolate a real external boundary,
   but must not skip the chain under test. An unsupported native input remains uncovered; a nearby path is not equivalent coverage.
4. Assert: derive expected behavior from requirements or an independent contract, not from the implementation under test.
   Check the resulting state and relevant persisted, file, data, or external effects; include reload/reopen/restart when relevant.
5. Capture: preserve the action, result, assertions, and evidence links in verification records.
6. Clean up: remove only instances and scratch state created by this run; preserve evidence and confirm it survives cleanup.

Use the parts appropriate to the surface: a short-lived tool may need version, input, output, and exit checks
instead of server readiness. Missing prerequisites or tools make the affected checks blocked or unexecuted;
they do not authorize installation, external operations, or fabricated commands.
The real-entry and chain-coverage requirements apply when claiming user-journey behavior.
Unit tests may directly call internal logic or use suitable doubles; their results do not replace real journey acceptance.

For every verification, distinguish:
unit tests, simulated integration, real environments, and manual acceptance.
A simulation passing must not be reported as a real device or on-site verification passing.

Test records should include:
case, actual tested revision/build or working-tree fingerprint, instance and environment (including mocked boundaries),
actual entry/input path, expected and actual results, relevant side effects, evidence, cleanup, and uncovered scope.
Checks not run or blocked must not count as passes.
Results belong to the tested object. After source, build, or integration changes, rerun affected checks;
retain old evidence without presenting it as proof of the changed object.

Unrelated changes do not require repeatedly running the entire test suite.
Major business, persistence, concurrency, and release changes must pass the corresponding full gates.

## 9. Prevent Architectural Drift

The following trigger a targeted review, not an automatic comprehensive refactor:

- The same rule must be changed in multiple places;
- Fixing one issue frequently breaks another entry point;
- Modules develop circular dependencies;
- Pages or routes keep accumulating business workflows;
- Testing one rule requires starting the entire system;
- A new protocol forces general business modules to recognize vendor details;
- One file contains responsibilities that change for several unrelated reasons.
- The same failure repeatedly requires local patches, manual reminders, or duplicated setup.

Line counts are a signal, not a mechanical criterion for splitting files.

The review should state:
the actual problem, impact, smallest adjustment, and regression verification method.
Prefer small steps that preserve behavior; avoid large simultaneous structural and functional changes.
For repeated failures, identify the shared cause and consider the smallest interface, type, boundary,
tooling, or workflow improvement with a regression check. Implement only within the authorized scope;
record broader changes as a concrete proposal, not permission for unlimited refactoring.

## 10. First-Round Output

First provide:

1. Project understanding and key assumptions.
2. Current structure and evidence; explicitly state when a new project has no implementation yet.
3. Recommended architecture and reasons for not choosing a more complex approach.
4. The layering contract: module and layer responsibilities, actual or planned paths, public contracts, allowed and forbidden dependencies, state ownership, verification methods, and reasons for merging or omitting layers.
5. Two core workflows, plus the initial core-feature map scope, location, driving methods, and evidence gaps.
6. Key risks, constraints, test methods, verification-environment gaps, and ownership/isolation if parallel work is needed.
7. The minimum list of documents to create or update.
8. A small number of key questions requiring user decisions.

Initialize after user approval.
At completion, check documentation links, effective rules, actual verification, and tool entry points.
Check the feature map's entries, index links, reading triggers, and evidence labels; map coverage does not imply that all journeys have passed live verification.
Check the layering contract's responsibilities, paths, dependencies, ownership, and verification methods item by item; identify anything not implemented or not verified;
do not declare engineering readiness merely because the directory structure is complete.
