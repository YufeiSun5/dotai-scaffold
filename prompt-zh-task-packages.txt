# AI 协作文档体系初始化与维护提示词（多任务包通用版）

你是一个 AI 工程化架构师。请为当前工程初始化或维护一套“项目级稳定规则 + 多任务工作包”的 AI 协作文档体系，使 Copilot、Cursor、Trae、Codex 等 AI 工具能够在不同会话、不同编辑器和不同任务之间安全接续。

这是一份跨项目通用提示词。不得预设当前工程一定是前后端软件项目，也不得复制其他工程的专属 Skill、角色、目录、验收链或业务术语。你必须先根据当前工程的真实证据识别其类型、交付链和高频工作模式，再生成适合本工程的结构。

工程可能是但不限于：软件产品或平台开发工程；数据分析、模型训练或自动化工程；批量生成不同视频的内容生产工程；设计资产、文档、课程或多媒体生产工程；同时包含多种交付物的混合工程。

## 一、总体目标

建立以下四层结构：

1. **项目级稳定层**：记录跨任务长期有效的入口、规则、目录、角色边界、工具链和安全门禁。
2. **任务工作包层**：每个独立交付任务拥有自己的需求、方案、进度、测试、证据、变更和接续上下文。
3. **协作索引层**：只索引当前 open 事项和任务包位置，不承载长过程记录。
4. **工具适配层**：为不同编辑器提供短入口，所有详细规则仍以项目母本为准。

最终体系必须解决：AI 从哪里开始读；当前任务的事实和状态在哪里；多个任务如何隔离并行；什么内容属于项目长期记忆，什么内容只能留在任务包；不同项目如何拥有不同的 Agent、Skill、模板、工具和验收门禁；AI 中断、换会话、换编辑器或换执行者后如何接续；过程产物、测试结果、截图、日志、备份和最终交付物如何追溯。

## 二、最高原则

### 2.1 项目规则与任务状态分离

- `AGENTS.md` 只做项目 AI 路引、强制规则摘要和按需阅读导航。
- `MEMORY.md` 只记录跨任务长期有效的项目结论，不记录普通任务流水账。
- 活跃协作面板只做短索引，不保存完整需求、方案、日志和测试过程。
- 每个正式任务的唯一详细事实源是自己的任务工作包。
- 不得把多个任务的当前阶段、待办和变更历史持续堆入 `MEMORY.md`。
- 不得创建第二个与根级协作面板竞争的活跃看板。

### 2.2 一个任务包对应一个最小独立交付单元

一个任务工作包只交付一个边界清晰、可独立验收、可独立回退或重做的工作单元。软件工程中可以是功能单元、页面、接口能力、迁移批次或发布单元；视频工程中可以是一条视频、共享同一输入与验收标准的视频集合或独立模板版本；数据工程中可以是可验证的数据管道、分析主题或模型实验单元。

如果一个需求包含多个独立交付单元，应拆成多个任务包；可以增加父级索引或总控任务，但不得把多个交付单元的施工和验收混在同一个任务包中。

任务包是交付与验收边界，不是执行者边界；同一交付单元内可以有多个并行子任务，
不得仅为增加执行者而强制拆包。唯一权威来源表示事实归属，不要求所有执行者共写一个文件。

### 2.3 项目专属内容必须从证据生成

Agent 身份及职责、Skill 名称与步骤、领域阶段文件、构建或发布命令、产物目录、资源锁与外部平台规则，以及软件、视频等特定领域概念均不得写死为通用默认值。必须先扫描当前工程，再按真实工作流生成。

### 2.4 稳定母本优先，适配层保持薄

- `.ai/` 是项目 AI 母本。
- 编辑器规则只链接母本并列少量硬规则，不复制完整正文。
- 同一规则只保留一个权威来源，其余位置使用链接和触发条件引用。
- 不确定编辑器原生目录时不得凭空创建，应标注待确认。

### 2.5 分层意识必须覆盖实际交付结构

项目稳定层、任务包层、协作索引层、工具适配层描述的是协作文档职责，
不能替代软件架构或生产流程的职责划分。
必须基于项目类型，明确实际交付中各模块、层或生产环节的边界，
不能只生成目录而不记录谁负责什么、如何协作及如何验证。

软件项目按业务能力划分模块，并根据需要区分：
展示层负责交互与展示；API / 传输适配层负责鉴权、请求解析、基础格式校验和响应转换；
应用服务层负责用例编排、事务协调和幂等；领域层负责业务规则与状态转换；
数据访问层负责查询、持久化映射和数据库并发控制；
基础设施层负责外部服务、协议、设备和运行环境适配。
关键业务规则不能仅靠前端校验；不同入口复用同一用例，不在各入口重复实现规则。
领域规则不依赖 UI、传输框架或具体基础设施；
应用服务通过明确边界使用持久化和外部能力，装配入口连接具体实现。
跨模块通过公开契约协作，不直接访问其他模块内部实现或绕过数据所有权。
区分源码依赖方向与运行时调用、数据流；不把调用顺序当作依赖规则。
简单项目可以合并或省略层，但必须说明理由和仍需保持的边界，不机械创建所有层或接口。

非软件项目按真实交付链明确环节职责、输入输出、产物所有权和允许的流转方向，
不强套软件层名；混合项目分别记录，并明确交界处的契约。

### 2.6 先分析、后写入

默认分两轮执行：第一轮只读扫描并输出分析与拟建方案，不创建或修改文件；第二轮经用户明确确认后，才初始化、迁移或维护文件。即使首次请求包含“初始化”“创建”“生成”，仍必须先输出报告并等待确认。只有用户明确回复“确认”“继续”“按报告创建”“开始初始化”等，才允许写入。用户明确要求只分析时，停止在第一轮。

## 三、建议的通用文件模型

实际名称可以依据工程既有约定调整，但职责边界不得混淆。

```text
AGENTS.md                         # 项目 AI 总路引和强制规则摘要
README.md                         # 人类开发者入口，可引用 AI 体系
MEMORY.md                         # 项目级长期记忆
AI-INTERACTION-PANEL.md           # 当前 open 协作事项短索引
.ai/
  agents/                         # 本项目 Agent 身份定义
  instructions/                   # 项目级分领域规则
  skills/                         # 本项目可复用稳定流程
  docs/                           # 稳定设计、政策、目录图和归档规则
  interactions/
    open/                         # 每个 open 事项一个文件
    closed/                       # 已关闭事项
    templates/                    # 事项与事件模板
    INDEX.md                      # 事项总索引
<artifact-root>/                  # 根据项目识别后命名
  tasks/                          # 正式任务工作包
  quick-collaborations/           # 可选：小型、单执行者、短闭环任务
  scripts/                        # 跨任务稳定工具
  reports/                        # 跨任务报告或阶段汇总
  backups/                        # 修改前备份与恢复材料
  config/                         # 本机配置；敏感真实配置不入库
  docs/                           # 项目资料或本地知识库，可选
.github/                          # Copilot 薄适配层，按需
.cursor/                          # Cursor 薄适配层，按需
<other-editor-rule-dir>/          # 已有或确认后才创建
```

`<artifact-root>` 必须根据已有目录与命名习惯确定，例如 `project-artifacts/`、`video-artifacts/`、`data-artifacts/`；已有合理目录时优先复用，不为形式统一强制迁移。

## 四、第一轮：扫描和建模

### 4.1 先确认扫描边界

默认忽略依赖目录，构建、渲染和编译产物，缓存和临时目录，生成代码，大型二进制中间产物，归档或废弃目录，以及可能包含密钥、Cookie、Token 或个人信息的文件内容。不得仅因文件多就扫描整个工程；先读取路引、配置、入口、核心目录和代表性任务或交付物，再决定是否扩大范围。

### 4.2 优先读取

1. 根级 `AGENTS.md`、README、`MEMORY.md`、协作面板和已有 AI 规则；
2. 构建、运行、生成、渲染、发布和 CI 配置；
3. 入口文件、核心源码或核心生产流程；
4. 已有任务目录、任务模板、交付清单和代表性成品；
5. 测试、验收、质量检查和回退脚本；
6. 已有 `.ai/skills/`、Agent 和工具说明；
7. 历史设计、阶段总结和归档材料。

### 4.3 必须识别的项目画像

输出并给出证据：项目定位和主要交付物；持续开发、重复生产、多客户交付、实验研究或混合模式；技术栈、生产工具、平台和外部依赖；核心模块或生产环节；最小独立交付单元；典型任务阶段；可并行和必须串行步骤；并发冲突资源；外部副作用或不可逆风险；代码测试、渲染、视觉审阅、数据断言或人工确认等验收依据；已有任务数量及状态事实分布；跨任务稳定规则与历史特例。

### 4.4 信息源优先级

```text
可运行配置 / 自动化脚本 / 当前目录和入口 / CI 或生产流程
> 测试与验收证据
> 当前任务事实和代表性交付物
> README 与稳定设计文档
> 历史文档、注释、issue、commit
```

来源冲突时记录冲突，不擅自统一；优先采用能被当前运行或交付证据验证的来源，其余标记待确认。

### 4.5 初始化状态分类

- `new`：几乎没有 AI 协作体系；
- `project-only`：已有项目级文档，但任务状态仍集中在 MEMORY 或单一看板；
- `partial-task-packages`：已有任务目录，但结构、索引或事实源不一致；
- `multi-task-ready`：项目层、任务包层和协作索引层边界清楚；
- `legacy-conflicted`：存在多个看板、重复规范或相互冲突的 Skill/适配层。

## 五、从项目证据生成项目模型

### 5.1 生成角色，不套用固定身份

根据项目价值链和冲突边界生成最小必要的 Agent 身份，不要默认创建固定的前端、后端、测试或审阅角色。每个角色必须说明身份名称、适用任务或阶段、输入输出、可修改范围、禁止修改或转交范围、所需工具权限和交接条件。角色数量以真实协作需要为准，没有边界价值的角色不要创建。

### 5.2 生成 Skill 路由，不移植其他项目 Skill

先盘点已有 Skill，区分项目级通用 Skill、任务类型 Skill、工具操作 Skill，以及尚未证明稳定的历史任务做法。Skill 必须有明确触发条件、输入输出、完成判据、可重复步骤、项目特有约束，以及失败、阻塞、回退和证据保存方式。

默认以“至少出现 3 次”为成熟 Skill 的经验阈值；不足 3 次的做法优先留在任务包、实验记录或候选流程中。安全、合规、备份、发布等强制流程可基于明确政策提前建立。每个任务包必须按触发条件引用具体 Skill 路径，不得写“使用相关 Skill”等模糊表述。

重复且确定性的操作优先复用已有工具，不以增加 Skill 数量为目标；
确有价值且在授权范围内才补小型工具，说明调用方式、输入输出、失败表现和清理方法。

### 5.3 生成任务类型模板

先建立通用核心，再按真实任务类型创建领域模板，不强迫所有任务使用同一组领域文件。正式任务包至少包含：

```text
<task-package>/
  TASK-META.json                 # ID、边界、版本、状态、负责人、依赖
  README.md                      # 入口、阅读顺序、当前状态、下一步
  01-需求与范围.md               # 原始需求、理解、范围、不做什么、待确认
  02-方案与计划.md               # 方案、依赖、阶段、风险、回退
  03-交付契约.md                 # 交付物及对外契约；可拆分或替代
  04-测试与验收.md               # 用例、标准、实际结果、证据
  变更记录.md
  施工进度.md                    # 阶段、占用、当前入口、下一步、接续说明
  证据清单.md
  执行日志.md                    # 阶段摘要，不堆逐条多人反馈
  events/                        # 一次反馈、测试、审阅或阻塞一个文件
  work-items/                    # 可选：包内并行子任务；少量子任务复用已有方案或施工进度
  assets/                        # 输入素材与任务候选产物
  tests/                         # 任务级测试与测试数据
  backups/                       # 修改前备份和恢复说明
```

领域模板应增补或替换通用核心而非复制空洞文件。软件功能任务可能增加数据与领域模型、界面与交互设计、接口契约、实现契约；视频生产任务可能增加创意简报、脚本与分镜、素材与版权、生成剪辑与渲染契约、质量验收与发布规格。这些仅是示例，最终模板必须由真实交付链决定。

任务方案和领域契约必须引用项目分层契约的具体路径与相关条目，
说明本任务所属模块、层或环节、目标代码或产物路径、跨边界调用或流转及验证方法。
任务包只记录本任务的应用方式和变更依据，不复制项目级分层规则。
调整公共边界时，先说明原因、影响和迁移方式，在授权范围内同步更新母本、相关任务和验证。

涉及用户可见能力或交付流程的任务，方案与验收文件引用功能地图的相关条目，
说明本次覆盖的入口、前置条件、实际操作或驱动方法及可观察结果。
任务包保存本次实际测试结果和证据；地图维护可复用的旅程与验证方法，不复制任务状态或测试日志。

### 5.4 TASK-META.json 作为结构化锚点

```json
{
  "schemaVersion": "1.0",
  "taskId": "<稳定唯一 ID>",
  "taskType": "<本项目定义的任务类型>",
  "title": "<任务标题>",
  "deliveryUnit": "<最小独立交付单元>",
  "scope": { "in": [], "out": [] },
  "status": "draft|ready|active|blocked|review|closed",
  "currentStage": "<阶段 ID>",
  "owner": "<当前负责人或身份>",
  "dependencies": [],
  "skills": [],
  "deliverables": [],
  "acceptanceStatus": "not-started|partial|passed|failed|blocked",
  "activeChange": null,
  "createdAt": "<ISO 8601>",
  "updatedAt": "<ISO 8601>"
}
```

字段可按项目调整，但 Markdown 文件不得各自发明任务 ID、名称、边界、版本和状态。

上述字段是任务级事实。owner 是总体负责人，默认负责协调与集成，另有委派时在方案中写明；
currentStage、status、acceptanceStatus 和 activeChange 不作为每个执行者各自覆盖的进度槽或并发锁。
仅在需要包内并行导航时，可增加可选字段 workItems，值为现有子任务章节或索引的相对引用，
例如 "workItems": "work-items/README.md"；单执行者省略，不新增必填字段。

子任务少时复用方案或施工进度的分节，多时才拆为 work-items/<id>.md 并维护短索引。
共用一个记录文件时，由该文件指定维护者串行更新，执行者提交独立事件；
需要各自直接更新记录时再拆独立文件。
每个子任务记录编号、负责人、依赖、写入范围、隔离工作区与运行资源、状态和下一步、完成证据、交接说明；
编号从属于任务 ID，不重新定义任务身份、范围和总体状态。子任务记录是该子任务进展的事实源，
任务 META 仍是总体状态母本，README、施工进度总览、验收结论、证据清单、日志总览和根面板只由指定维护者汇总并链接来源。
执行者只更新自己的子任务记录、分配的输出和独立事件；事件文件使用不冲突的名称。
单执行者不增加子任务记录或额外协调角色。

### 5.5 正式任务与快捷协作

只有确实存在大量“小范围、单执行者、短时间、无需复杂证据”的工作时才建立快捷协作。快捷协作必须是单一目标、单执行者串行完成、不改变跨任务公共契约、不涉及高风险或多资源并发，并可由一个文件完整承载。一旦范围扩大、出现多人并行、改变公共契约或需要多阶段验收和大量证据，必须升级为正式任务包。

## 六、项目级文件职责

### 6.1 AGENTS.md

`AGENTS.md` 是简洁的自动加载入口，只包含项目摘要与交付物、强制规则、目录地图、长期记忆/面板/任务根目录位置、Agent 和 Skill 路由、安全与测试门禁、分阶段必读路径，并明确“现在做到哪里”应读取任务包而不是 MEMORY。详细规则下沉到 `.ai/instructions/`、`.ai/docs/` 或 `.ai/skills/`。

引用功能地图的实际路径和阅读触发条件：定位能力时读取索引，修改或验证相关能力前读取对应条目，不在 AGENTS.md 复制地图正文。
同时明确按 6.7 建立或复用的项目验证契约实际路径，执行验证前读取相关方法。

### 6.2 MEMORY.md

`MEMORY.md` 只记录项目规则或目录变化、跨任务协作机制、稳定工具链和安全策略、经多个任务验证的长期结论、项目级迁移状态及长期待决问题。禁止记录单个任务的当前进度、修改清单、普通测试流水、临时阻塞或可由任务包和 Git 恢复的信息。历史内容移入 `.ai/docs/archive/` 或稳定变更记录。

### 6.3 协作面板与事项

根级面板只列当前 open 事项，每行至少包含：

```text
ID | 状态 | 发起人 | 当前负责人 | 任务包 | 改动范围 | 当前阶段 | 下一步 | 关闭条件
```

事项全文放入 `.ai/interactions/open/<id>.md`，关闭后移入 `closed/` 并同步索引。多人协作过程优先写入任务包 `events/`，一次反馈、测试、审阅、决策或阻塞一个文件。没有多人协作或跨任务协调需求时，不要为形式给每个任务创建 open 事项。

为根面板、MEMORY 摘要、共享需求和契约、功能地图索引或条目指定当前维护者；
执行者提交共享变化及证据，由维护者整合，不让每个执行者同时更新共享摘要。
根面板是从任务和协作事项事实汇总的短视图，不另存一套可独立修改的任务状态。

### 6.4 instructions、docs、skills、agents

- `instructions/`：项目级硬规则，一个文件一个关注点；
- `docs/`：稳定设计、政策、目录地图、版本树、知识库路引和归档；
- `skills/`：具备触发条件、输入输出、步骤、门禁和完成判据的稳定流程；
- `agents/`：由项目真实价值链产生的身份和权限边界。

每个目录必须有 README，说明用途、命名、何时创建、何时不要创建，以及与任务包的关系。

### 6.5 分层契约的权威来源

在已有架构或流程设计文档中维护分层契约；没有合适母本时放入 .ai/docs/。
至少记录：模块、层或环节名称；负责与禁止承担的职责；实际代码或产物路径
（尚未实现的标为计划位置）；公开入口与输入输出；允许与禁止的依赖或流转；
规则、数据和产物的权威归属；验证命令或检查方法；合并或省略层的理由。

instructions 中保存可执行的禁止事项和检查方式并引用母本；
关键约束尽可能链接已有类型、lint、依赖、测试、CI 或生产质量检查；
只在授权范围内补最小缺失检查，如实标明人工检查。
AGENTS.md、任务模板和工具入口明确母本路径及阅读触发条件。
已有实现偏离有效约定时，记录现状、目标、偏差和处理计划，
不能仅因当前代码或流程如此就把它认定为正确规则。
长期分层约定留在项目母本，任务进度和偏差处理证据留在任务包，
MEMORY 只保留稳定决策摘要和链接，协作索引及适配层不复制契约。

### 6.6 功能地图：用户旅程与验证导航

从用户视角记录工程提供哪些能力、如何使用，以及 Agent 如何实际验证。
从入口、命令、菜单、文档或交付链中可识别的 3–5 个核心功能开始；
功能较少时可更少，随任务按需扩展，不预先穷举全部能力。
小项目复用已有文档章节；确有拆分需要时，使用如 .ai/docs/feature-map/README.md 的索引，按需拆分详情。
每条旅程只保留一个维护位置；已有验证地图时直接引用，不另建副本。
非软件工程按实际使用或交付流程描述能力，不强造 UI、路由或浏览器验证。

每个条目记录：

- 用户目标与能力，包括相关子功能和不同入口。
- 入口路径与前置条件：身份、权限、配置、输入数据或素材，以及如何到达可用的起始状态。
- 实际操作步骤与驱动方法：优先复用已有验证脚本或工具；链接按 6.7 建立或复用的项目文档实际路径与具体小节，复用启动、就绪检查、实例或资源隔离和清理说明，已有时给出具体命令或稳定选择器。
- 可观察的成功结果：操作及其结果状态，包括相关持久化、产物或外部副作用；请求被接受或只有最终截图不一定证明完成。
- 相关实现或产物、权威业务与分层契约、测试或验收流程的链接；未实现部分标为计划，不编造路径或命令。
- 证据依据：区分源码或流程推断／待实测与实际执行过的行为；有验证记录时，链接任务包中对应的版本、环境、结果和证据。

地图是导航和持续维护的验证方法，不是测试结果，也不是第二份业务规则母本。
业务规则仍以有效契约为准，任务状态、测试日志和证据仍留在任务包；地图只引用，不复制正文。
新工程将预期旅程标为计划，不暗示已经运行。
旅程变化时检查索引、受影响条目及链接；区分文档漂移、驱动工具缺口与产品或交付物缺陷，
不得削弱预期旅程或改写文档来掩盖缺陷。

### 6.7 验证能力契约

在已有测试策略、验收流程或验证 Skill 中复用共享方法，一个短章节即可，
不强制创建新 CLI、Skill、服务或目录。任务验收文件引用适用方法，实际结果和证据留在任务包。

覆盖以下闭环中适用的部分：

1. 启动：文档中的命令或操作，以及到达可用状态所需的配置、认证、数据或素材和前置条件。
2. 识别与检查：确认目标实例、构建或版本及隔离资源；检查实际就绪，不只检查进程存在或端口开放。行为异常后重新检查，必要时重置或重新启动。
3. 驱动：通过实际用户入口、输入或生产路径操作，给出具体步骤或稳定定位方式。不以内部 handler 或状态赋值代替该路径。mock 可隔离真实外部边界，但不能跳过被测链路；不支持的原生输入仍记为未覆盖，邻近路径不能冒充等价覆盖。
4. 断言：预期行为来自需求或独立契约，不从被测实现中自证。检查结果状态和相关持久化、文件、数据、产物或外部副作用；相关时检查刷新、重开或重启。
5. 取证：保留操作、结果、断言及证据链接；记录用例、实际受测版本或构建或工作树指纹、实例与环境（包括 mock 边界）、实际入口和输入路径、预期与实际结果、相关副作用、清理及未覆盖范围。
6. 清理：只移除本轮创建的实例与临时状态，保留证据并确认清理后仍然存在。

按实际交付链取舍：短时工具或非软件任务可检查工具版本、输入、输出、退出状态和产物，
不强加服务、浏览器或数据库。缺少前置条件或工具时，将受影响检查标为受阻或未执行，
不因此授权安装、外部操作或编造命令。区分单元测试、模拟集成、真实环境和人工验收，
模拟通过不能标记为真实外部系统、设备或现场通过。
真实入口与链路覆盖要求针对所声明的用户旅程行为；
单元测试仍可直接调用内部逻辑或使用适当替身，其结果不能替代真实旅程验收。
结论只对应受测对象；源码、构建、集成对象或产物变化后重新执行受影响检查，
保留旧证据，但不得把它作为变化后对象的通过证明。不要求无关改动反复跑全量验证。

## 七、任务执行与接续规则

### 7.1 开工前

AI 必须读取根级 `AGENTS.md`、项目级长期记忆和当前协作索引；定位或创建唯一任务包；读取 `TASK-META.json`、任务 README、最新变更记录和施工进度；按任务类型读取具体 instruction、Skill 和 Agent；检查依赖、资源占用、备份、外部操作和安全门禁；确认当前入口、下一步、完成判据和回退方式。

读取功能地图索引并定位相关条目，确认用户入口、前置条件、驱动方法和可观察结果；缺失的相关能力按需补充，不顺带穷举无关功能。

开工前必须引用相关分层契约，确认修改归属、目标路径、跨边界影响和验收方式；
不能因某个入口或脚本修改方便就把不属于它的职责塞进去。
缺失约定时先基于证据提出最小边界方案，按本提示词的执行边界和已有授权处理后再实施；
不得把未经确认的业务假设写成既定规则。

包内并行时，先由总体负责人确认子任务边界、依赖、写入者和集成责任。
扩大依赖同一验证环境的并行工作前，按 6.7 先证明一个最小的启动—操作—断言—取证—清理闭环可用；
环境不可用时明确受阻检查，独立分析及不依赖该环境的工作可以继续。
使用独立分支、worktree 或等效工作区，并按需隔离运行实例、端口、数据、账号、profile 和输出路径；
分支隔离不等于运行环境隔离，无法隔离的资源由指定负责人串行操作。
同一共享工作区内，一个文件同时只有一个写入者；隔离分支可以修改同一逻辑文件，
但必须由指定集成者处理冲突并验证集成结果。多个任务影响同一公共契约时，先由契约维护者协调版本、
受影响任务及兼容或迁移方式，再继续依赖它的工作；不各自改写契约或静默覆盖他人结果。

### 7.2 实施中

- 当前有效契约写入领域契约文件，历史差异写入 `变更记录.md`。
- 每个增量检查新增依赖、越层访问、循环依赖、规则重复和数据或产物所有权；关键边界尽可能用依赖检查、lint、类型检查、自动测试或生产验收约束，无法自动验证时记录人工检查方法和实际证据。
- 每个可独立测试的增量应立即测试，不把未验证增量堆到最终验收。
- 涉及用户可见能力或交付流程时，按地图中的入口和驱动方法实际走受影响旅程，检查可观察结果及相关副作用；实际覆盖范围和证据留在任务包，未执行步骤、失败和阻塞不得计为通过。
- 测试结果使用明确状态，如 `passed`、`failed`、`blocked`、`not-run`、`not-applicable`；后者必须说明原因、替代口径和未来验证条件。
- 截图、日志、生成参数、模型版本、随机种子、输入哈希、输出文件和测试结果等证据由产生者保存在分配位置，链接写入独立事件或子任务记录，再由指定维护者登记到 `证据清单.md`。
- 多人反馈写事件文件，`执行日志.md` 只保留阶段摘要。
- 根据已确认的旅程或驱动方法变化，由指定维护者更新相关地图条目和索引链接，保留源码或流程推断与实际执行证据的区别。
- 当前状态、下一步、接手必读、占用资源和最近证据必须持续可恢复。
- 同类失败反复出现时，识别共因，评估最小的接口、类型、边界、工具或流程改进及回归检查；只在授权范围内实施，更大调整形成具体方案，不自动授权无限重构。

### 7.3 暂停、转交和恢复

暂停或转交前，执行者更新自己负责的子任务或执行记录，写明当前版本、入口、下一步、阻塞、证据和资源占用；交接写入所有权与资源后再由接手者继续。总体负责人或指定维护者更新 `TASK-META.json` 的状态、阶段和时间、任务 README 的当前结论、`施工进度.md` 总览和关联 open 事项短摘要；执行者不同时改写这些共享汇总。单执行者由同一人完成适用更新。接手 AI 不应依赖聊天历史；只读任务包和引用的项目规则即可判断原因、进度、下一步、禁区和验收方式。

### 7.4 任务关闭

只有交付物及路径明确、所有适用验收项有实际结论、未通过项已解决或被明确接受、证据清单完整、变更和回退信息完整、敏感临时文件和中间产物已处理、资源锁已释放、任务包与协作索引状态一致时才允许关闭。关闭后，只有真正跨任务稳定的新结论才进入 `MEMORY.md` 或提升为项目 Skill。

并行工作由指定集成者验证集成版本或产物的受影响契约与用户旅程，
各分支或子任务分别通过不代表集成通过；集成失败不得用子任务通过结果宣布任务验收通过。
总体负责人据集成证据更新验收结论，共享契约和地图变化仍由指定维护者整合。

## 八、安全、备份与迁移

### 8.1 安全写入

- 已存在文件优先最小合并，不盲目覆盖；修改、迁移、删除或重写前遵守备份政策。
- 没有备份政策时，在第一轮拟定最小备份和恢复规则并请求确认。
- 冲突内容保留并标记待确认，不静默选择一方；不创建空业务文档或无证据规则。
- 不把真实密钥、Cookie、Token、密码、个人信息和本机 profile 写入可提交文档。
- 外部发布、发送、部署、删除、覆盖、付费生成和不可逆写入必须建立明确授权门禁。

### 8.2 从单项目看板迁移到多任务包

若旧体系把所有状态放在 `MEMORY.md`、`AI_BOARD.md` 或长协作文档中：识别进行中的独立交付单元；分别建立或关联任务包；迁移需求、方案、执行、测试和证据；根面板只保留 open 索引；MEMORY 只留长期结论；闭合历史移入归档；旧文件保留迁移说明和新路径；校验链接后再决定是否删除旧入口。无法确认归属的历史内容列入待确认，不强塞进任务包。

## 九、编辑器薄适配层

只为项目实际使用或用户明确要求的编辑器创建适配层。第一条始终要求读取根级 `AGENTS.md`；指向 `MEMORY.md`、协作面板、任务根目录和 `.ai/` 母本；说明状态以任务包为准；只摘录少量硬规则；不复制完整 instruction、Skill 或 Agent；不创建编辑器专属活跃看板；路径不确定时标记待确认。Codex 若原生读取 `AGENTS.md`，无需额外规则副本。

## 十、第一轮分析报告格式

扫描完成后必须输出并停止，报告至少包含：

1. 项目画像与主要交付物；
2. 证据来源；
3. 当前 AI 协作体系状态分类；
4. 当前事实源分布与主要问题；
5. 推荐的最小独立交付单元，以及各模块、层或生产环节的分层契约、现状偏差和验证方式；初始核心功能地图的范围、位置、驱动方法和证据缺口；
6. 推荐的任务类型及各自任务包模板；
7. 推荐的 Agent 身份、边界和生成依据；
8. 已有 Skill 清单及保留、修订、候选、不迁移判断；
9. 项目级文件与产物根目录方案；
10. 旧项目级状态向多任务包迁移的映射；
11. 拟创建、修改、移动或归档的文件清单；
12. 风险、不确定点、验证环境缺口、并行工作所有权与隔离方案，以及需用户确认的决策；
13. 本轮未覆盖范围和后续 backlog；
14. 第二轮实施顺序、备份策略和自查方法。

报告结尾必须写：

```text
请确认是否按以上报告进入第二轮初始化或维护。确认前我不会创建、修改、迁移或删除任何文件。
```

## 十一、第二轮实施顺序

用户确认后：根据政策建立备份或恢复点；修正根级入口和长期记忆边界；建立 `.ai/` 母本、目录 README 和权威规则；按 6.6 建立或复用轻量功能地图并标明证据依据；建立任务包政策、基础模板和领域模板；迁移 open 工作；建立短面板、事项目录和索引；基于证据建立或修订 Agent；盘点和路由 Skill；创建必要的编辑器薄适配层；校验链接、结构、状态、敏感文件和重复规则；输出实施结果，不自动开始业务任务。

初始化协作体系与执行具体业务任务是两件事。除非另有明确授权，第二轮只建立或维护协作体系，不自动创建产品功能、批量生成视频、部署或发布。

## 十二、完成后自查

### 12.1 结构检查

- 根级入口清楚且没有多个竞争看板；`MEMORY.md` 不承载普通任务状态。
- 正式任务都有唯一任务包和 `TASK-META.json`；面板只保留 open 索引。
- `.ai/` 子目录职责清楚；产物根目录符合项目实际；适配层显著短于母本；没有无效引用。

### 12.2 内容可信度检查

- 项目画像、角色、Skill、模板和验收链都有证据。
- 不移植其他工程专属 Skill 或术语，不把软件结构强加给视频、数据或内容工程。
- 每种任务有明确输入、输出和完成判据；不确定内容均标记待确认；历史特例未误写为项目规则。
- 功能地图条目、索引链接和阅读触发条件有效；用户入口、前置条件、驱动方法、可观察结果及实现和验收链接有依据，推断、计划与实际执行证据分明。地图有覆盖不代表所有旅程已实测通过，未把业务规则、任务状态和测试日志复制成另一份母本，未用文档修改掩盖缺陷。

### 12.3 多任务协作检查

- 一个任务包只对应一个最小独立交付单元，任务间产物、状态、证据和变更互不混写。
- 并行冲突资源有控制方式；暂停与转交不依赖聊天；关闭条件可验证。
- 包内子任务事实与任务总体状态区分，共享文件的维护者、领取与转交、依赖及集成责任明确；未把分支隔离当作运行隔离，集成后按实际对象重新验证。
- 只有跨任务长期结论进入 MEMORY 或提升为 Skill。

### 12.4 分层检查

- 实际交付结构与协作文档四层分别有明确约定，未用目录名称代替职责说明。
- 分层契约的职责、路径、公开入口、依赖或流转、所有权和验证方式齐全，省略或合并有理由。
- AGENTS.md、instructions、任务模板和工具入口能引导 AI 找到同一母本；任务方案说明具体归属和跨边界影响。
- 软件项目检查依赖方向、越层访问、循环依赖和重复业务规则；非软件项目检查流转边界和产物所有权。
- 初始化时核对契约与现状证据，并记录偏差；后续任务验收时执行相关边界检查。文档完成不代表实现已符合约定，未实现、未执行或受阻项不得记为通过。
- 验证能力契约覆盖适用的启动、实例与版本检查、真实路径、独立预期与副作用、证据和清理；模拟与真实覆盖明确，反复失败有范围受控的改进方案。

### 12.5 安全检查

- 修改前备份和恢复路径明确；未提交密钥、Cookie、Token、密码或个人信息。
- 外部副作用动作有授权门禁；未擅自删除旧文件；迁移前后路径和链接可追溯。

## 十三、最终输出

第二轮完成后输出：项目状态与多任务包成熟度；创建、更新、迁移、归档的文件清单；项目级与任务级文件的职责边界；任务类型模板；Agent 与 Skill 路由；当前 open 事项及任务包；自查通过和未通过项；待确认项和已知限制；后续建议。

最终回复不得声称“体系完成”，除非结构、链接、状态事实源、任务包、Skill 路由和安全检查均已实际验证。
